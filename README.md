# colorscheme-tools

Create, convert and render colourschemes from a single **`colorschemes.json`** per scheme.
Pure Python ≥ 3.11, standard library only. The package is `cstools`, with a CLI of the same name.

It is designed around accessibility: schemes are optimised and scored against a colour-vision model
(default: strong deutan, Machado 2009, CIEDE2000 on simulated colours).

## Install
```sh
pip install -e .            # provides the `cstools` command
# or, without installing:
PYTHONPATH=src python3 -m cstools --help
```

## Commands
| Command | Purpose |
|---|---|
| `cstools validate PATH…` | schema, reference and cycle checks |
| `cstools optimize RECIPE.toml -o OUT.json` | design a scheme: optimise editor roles and terminal colours from a recipe |
| `cstools build REPO [--targets …] [--schemes …] [--check]` | render every configured target of a theme repository (`--check` for CI) |
| `cstools render SCHEME.json --target NAME [--out DIR]` | one target for one scheme |
| `cstools score SCHEME.json [--json] [--model MODEL.json]` | colour-vision separation scores |
| `cstools inspect SCHEME.json` | which roles, derived colours and terminal slots use each base colour |
| `cstools rename-palette PATH… [--check]` | rename base colours to the naming rules, rewriting every reference |
| `cstools migrate OLD.json -o NEW.json [--recipe …]` | convert a schema v1 file to v2 |
| `cstools gallery REPO -o DIR [--extra-dumps DIR]` | offline HTML gallery with editor/diff/terminal previews and deutan simulation |
| `cstools targets` | list output formats |

## Targets
alacritty · kitty · wezterm · ghostty · rio · tmux · fish · starship · fzf · bat · delta · lazygit · eza · yazi ·
vim · neovim (Lua runtime with `setup()` options) · lualine

Each target is one module in `src/cstools/targets/`, found automatically. Adding a format means adding a file
with a `Target` subclass and a test. See [ARCHITECTURE.md](ARCHITECTURE.md).

## `colorschemes.json` in short
```jsonc
{
  "schema_version": 2, "id": "haze", "name": "Haze", "variant": "dark", "family": "haze",
  "palette":  { "bg": "#2d2f33", "fg": "#c0bdb5", "blue_pale": "#9ecfff", … },   // the only hex values
  "derived":  { },                                                                // optional formula overrides
  "roles":    { "syntax": { "keyword": { "fg": "indigo_dark", "italic": true }, … },
                "diagnostic": { … }, "git": { … }, "ui": { … } },
  "terminal": { "normal": { "black": { "raise": ["bg_alt", 0.06] }, "red": "amber_dark", … }, … }
}
```
Every colour is stored once. Roles and terminal slots are references (`"blue_pale"`, `"syntax.type"`) or formulas
(`mix`, `lighten`, `darken`, `raise`, `chroma`). Shared derived colours (cursorline, selection, diff backgrounds, …)
come from `scheme/defaults.py`. The JSON Schema is in [`schema/colorscheme.schema.json`](schema/colorscheme.schema.json).

## Theme repository layout
```
<repo>/colorschemes.toml        [project] name, lua_module · [build] schemes, targets
<repo>/<id>/recipe.toml         design input for `cstools optimize` (optional)
<repo>/<id>/colorschemes.json   source of truth
<repo>/<id>/…  colors/  lua/    generated by `cstools build`
```

## Development
```sh
PYTHONPATH=src python3 -m unittest discover -s tests
```
Tests that need external binaries (nvim, tmux, fzf, git, delta, eza, fish, lazygit, firefox) skip when the
binary is missing. Tests never write to the user's configuration or caches. `legacy/` holds the original
prototype scripts as a behavioural reference; they are not imported by the package.
